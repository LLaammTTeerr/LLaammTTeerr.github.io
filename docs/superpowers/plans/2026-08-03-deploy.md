# Deploy Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Put the site on the internet at `https://LLaammTTeerr.github.io`, built and published by CI on every push, with the chain's integrity checked before anything ships.

**Architecture:** A GitHub Actions workflow runs the same commands a developer runs — typecheck, test, build — then publishes `dist/` to GitHub Pages. **CI never runs `chain:build`.** The ledger is committed; CI verifies it and refuses to publish a build whose content disagrees with it. Rebuilding the chain in CI would mine against CI's clock and rewrite history that is meant to be frozen.

**Tech Stack:** GitHub Actions, `actions/deploy-pages`. No application-code dependencies.

**Decided with the author:**

| | |
|---|---|
| Repository | `LLaammTTeerr/LLaammTTeerr.github.io` |
| URL | `https://LLaammTTeerr.github.io` |
| Kind | **User site** — served from the domain root, so `base` is `/`, not `/blogchain` |
| First deploy | Ships **with** the demo corpus |

## Global Constraints

- **No module under `src/site/` may read the clock.** Two consecutive builds must be byte-identical — CI depends on this to be meaningful.
- **`verifyChain` must never throw** on untrusted input.
- **`verify.ts` and its transitive closure** (`canonical.ts`, `hash.ts`, `merkle.ts`, `types.ts`) must never reach a Node built-in or a bare package specifier — it runs in the browser.
- **Sealed blocks are frozen**; `chain.lock.json` is never rewritten for an existing block, and **never by CI**.
- **Zero dead links and every `src` resolves.**
- **Explorer chrome is English; author-facing content is Vietnamese.**
- `noUncheckedIndexedAccess: true`; `npm run typecheck` runs `tsc --noEmit && astro check`.
- `npm test` — 839 currently passing, green **both** with the demo corpus seeded (its current state) and after `npm run demo:clear`. **If a task clears it, seed it again** — the author asked for the corpus to stay.

### Task 1: Point the site at its real address

**Why first:** `site` is the placeholder `https://lamter.example`, a reserved TLD. Every URL in `/rss.xml` is currently valid RSS pointing at nothing, and the feed is the one output where a wrong value is baked into what readers subscribe to.

**Files:**
- Modify: `astro.config.mjs`
- Test: `tests/site/deploy-config.test.ts`

**The `base` trap.** `LLaammTTeerr.github.io` is a **user site**: it is served from the domain root, so `base` stays `/`. A *project* site (`user.github.io/repo`) needs `base: '/repo'`, and this is the single most common way a GitHub Pages deploy breaks. Set it explicitly with a comment saying which kind of site this is and why, so nobody later "fixes" it to `/blogchain` and 404s every URL.

- [ ] **Step 1: Write the failing tests**

```ts
it('points at the site\'s real address', () => {
  expect(SITE).toBe('https://LLaammTTeerr.github.io');
});

it('carries no placeholder host anywhere in the build', () => {
  // `.example` is a reserved TLD: a link to it is well-formed and resolves to
  // nothing, which is exactly the failure that survives review.
  for (const file of allBuiltFiles()) {
    expect(readDist(file)).not.toMatch(/lamter\.example|example\.com|your-handle/);
  }
});

it('serves from the domain root, as a user site does', () => {
  // A project site needs base '/repo'; a user site must not have one. Getting
  // this backwards 404s every url on the deployed site while every test that
  // reads `dist/` keeps passing.
  expect(BASE).toBe('/');
  expect(readDist('index.html')).not.toMatch(/href="\/blogchain\//);
});
```

- [ ] **Step 2: Run and confirm each fails for its own reason.**

- [ ] **Step 3: Set `site` and `base`** in `astro.config.mjs`.

- [ ] **Step 4: Check what else moved.** `/rss.xml` builds its URLs from `site`, so every link changes. Confirm the feed still validates and that no test hard-coded the old host — if one did, that test was asserting the placeholder and needs rewriting, not updating.

### Task 2: Build, check and publish from CI

**Files:**
- Create: `.github/workflows/deploy.yml`
- Test: `tests/site/workflow.test.ts`

**What the workflow must do, in order:**

1. `npm ci` — the lockfile, not `npm install`.
2. `npm run typecheck`
3. `npm test`
4. `npm run build`
5. Publish `dist/` to Pages.

**What it must not do.** It must never run `chain:build`. The ledger is committed history; regenerating it in CI would mine against CI's clock and rewrite blocks that are meant to be frozen. If a post has been edited without recording an amendment, `npm run build` already fails with the file and both hashes — **that is the guarantee, and CI's job is to let it fail**, not to paper over it by rebuilding.

**Add an explicit ledger check** before the build: verify the committed `chain.lock.json` with `verifyChain` and fail the job if it does not pass. `npm test` covers this indirectly, but the project's central claim deserves a step that says so by name in the CI log.

**Node version:** `engines.node` in `package.json` is the source of truth — read it and match, do not guess.

- [ ] **Step 1: Write the failing tests**

## Self-Review

**Spec coverage.** This plan implements no spec section; it is delivery. It does close the `site`/`base` placeholder carried since the site foundation.

**What this plan deliberately does not do.** It does not build `/verify` or search — those are the next plan. It does not touch `content/profile.md`'s placeholder links, which are the author's to fill.

**Risk that outlives this plan.** Once Pages is live, every push publishes. A post edited without running `chain:build` will fail the build and the site will simply not update — correct behaviour, but the author should know the failure mode is "nothing changes", not "a broken page appears". Say so in the final report.
