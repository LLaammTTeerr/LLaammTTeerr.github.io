# Browser Verifier Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a reader recompute the whole chain in their own browser, and any single post from its raw text through to its block hash — turning the project's central claim from an assertion into something anyone can check.

**Architecture:** No new verification logic. `src/chain/verify.ts` already proves the chain in Node and is guarded, by an import-graph test, against ever reaching a Node built-in — precisely so the same code can run in a tab. §7 calls that out as the key architectural constraint: *"verification logic lives in one pure module used by both the build and the browser. The same code proves the chain in Node and in the reader's tab, so the two cannot drift."* This plan adds the browser's entry points, not a second implementation.

**Tech Stack:** Astro islands, Web Crypto (`crypto.subtle`), existing `verify.ts`. No new runtime dependencies.

## Global Constraints

- **`verify.ts` and its transitive closure** (`canonical.ts`, `hash.ts`, `merkle.ts`, `types.ts`) must never reach a Node built-in or a bare package specifier. An import-graph test guards this — **this plan is the reason that guard exists**, so do not weaken it, and if a new import would break it, that is the design telling you something.
- **`verifyChain` must never throw** on untrusted input, for any input. The browser fetches over the network; a truncated or tampered response must produce a verdict, never an exception.
- **No module under `src/site/` may read the clock.** Two consecutive builds must be byte-identical.
- **Sealed blocks are frozen**; `chain.lock.json` is never rewritten.
- **No hard-coded colours** — eleven reader-selectable palettes; a test scans the whole stylesheet.
- **Explorer chrome is English; author-facing content is Vietnamese.**
- **§9: a page load touches no third party.** The verifier fetches only same-origin paths.
- **Zero dead links and every `src` resolves.**
- `noUncheckedIndexedAccess: true`; `npm run typecheck` runs `tsc --noEmit && astro check`.
- `npm test` — 872 currently passing, green **both** with the demo corpus seeded (its current state) and after `npm run demo:clear`. The corpus stays; re-seed if a task clears it.

## What §7 requires, in full

> `/verify` fetches `chain.json` and recomputes the chain in the reader's browser via Web Crypto, **streaming results per block**: block hash from header, Merkle root from transaction hashes, **each transaction's own hash recomputed from its fields**, the `gasUsed` and `value` sums, previous-hash linkage, and proof-of-work difficulty.
>
> Recomputing transaction hashes is not optional. Verifying only the Merkle root proves the recorded hashes are consistent with each other, not that they match the content displayed beside them — **a forged title would still verify clean.**
>
> Proof-of-work is checked against each block's own committed `difficulty`, with the chain-level `difficulty` as a floor.
>
> Each post page additionally offers **"Verify this transaction"**, which fetches that post's canonical source and hashes it live — closing the loop from raw text through to block hash.

### Task 1: `/verify` — recompute the chain in the tab

**Files:**
- Create: `src/pages/verify.astro`, `src/components/ChainVerifier.astro` (or an island script beside it), `src/styles/verify.css`
- Modify: `src/chain/verify.ts` (streaming entry point only — see below), `src/site/routes.ts`
- Test: `tests/site/verify-page.test.ts`, `tests/chain/verify-stream.test.ts`

**Streaming.** §7 says results stream per block. `verifyChain` returns everything at once, which is right for the build and wrong for a tab: on a long chain the reader stares at nothing, then gets a verdict. Add a streaming entry point to `verify.ts` — an async generator yielding one `BlockVerification` at a time — and **express `verifyChain` in terms of it** so there is one implementation, not two that can disagree. Do not change `verifyChain`'s signature or behaviour; 872 tests depend on it.

**What the page shows.** Per block, as it lands: height, period, and each check §7 names, individually pass/fail — block hash, Merkle root, every transaction hash, the `gasUsed` and `value` sums, `prevHash` linkage, proof-of-work against that block's own committed difficulty. A reader must be able to see *which* check failed, not just that something did.

**Without JavaScript** the page must still explain what verification is and that it needs JS, rather than rendering an empty shell. Everything else on this site works with JS off; this one genuinely cannot, so say so.

- [ ] **Step 1: Write the failing tests**

```ts
it('yields one result per block, in order', async () => {
  const seen = [];
  for await (const r of verifyChainStream(chain)) seen.push(r.height);
  expect(seen).toEqual(chain.blocks.map((b) => b.height));
});

it('agrees with verifyChain, block for block', async () => {
  // The guarantee that stops the two drifting. If this ever fails, the browser
  // and the build are proving different things.
  const streamed = []; for await (const r of verifyChainStream(chain)) streamed.push(r);
  expect(streamed).toEqual((await verifyChain(chain)).blocks);
});

it('catches a forged title, which a merkle-only check would not', async () => {
  // §7's stated reason for recomputing transaction hashes. Take a real block,
  // change a transaction's title, leave every recorded hash untouched.
  const forged = withForgedTitle(chain);
  const results = []; for await (const r of verifyChainStream(forged)) results.push(r);
  expect(results.some((r) => !r.ok)).toBe(true);
});

it('never throws, whatever it is handed', async () => {
  // The browser fetches this over the network. Truncated, tampered, wrong shape.
  for (const junk of hostileInputs()) {
    await expect((async () => { for await (const _ of verifyChainStream(junk)) {} })()).resolves.not.toThrow();
  }
});

it('says what it needs, with scripts disabled', () => {
  expect(readDist('verify/index.html')).toMatch(/JavaScript/);
});
```

- [ ] **Step 2: Run and confirm each fails for its own reason.**
- [ ] **Step 3: Add `verifyChainStream` and re-express `verifyChain` through it.**
- [ ] **Step 4: Build the page and its island.** The island imports from `src/chain/`, so confirm by measurement that no Node built-in reaches the bundle — a build that silently polyfills `node:crypto` would ship a verifier that works in tests and fails in a browser.
- [ ] **Step 5: Drive it in a real browser** — `npm run dev`, load `/verify`, watch it stream, and confirm it reports the live chain as valid. Then tamper with a served `chain.json` and confirm it reports the failure. Paste both into your report.
- [ ] **Step 6: Flip `verify` to `built: true`,** run the suite seeded and cleared, then commit — `feat(site): recompute the chain in the reader's browser`

### Task 2: "Verify this transaction" on a post page

**§7:** *"fetches that post's canonical source and hashes it live — closing the loop from raw text through to block hash."*

**The gap to close first.** The site serves each post as *rendered HTML*. Hashing that proves nothing: the committed `contentHash` is over the **normalized body**, and normalization plus markdown rendering are not reversible. So the canonical source has to be served.

Decide how, and justify it — the two candidates are a sibling file per post (`/tx/<slug>/body.txt` or similar) and embedding the body in the page. Weigh: page weight, whether a reader can fetch and re-hash it independently with `curl` and `sha256sum` (a property worth a great deal on this project), and what happens for a **pending** post. Say what you chose and why.

**What the control must prove**, end to end: the served body hashes to the transaction's committed `contentHash`; the transaction's own hash recomputes from its fields including that `contentHash`; and that transaction hash appears in its block's Merkle root. Anything less is a demo, not a verification — and if a step cannot be closed for pending posts, say so on the page rather than implying it was checked.

**Files:**
- Create: the canonical-source route, `src/components/TxVerifier.astro`
- Modify: `src/pages/tx/[slug].astro`
- Test: `tests/site/tx-verify.test.ts`

- [ ] **Step 1: Write the failing tests** — the served canonical source hashes to the committed `contentHash` for every post on the chain; the control is absent or honest for a post whose chain of evidence cannot be closed; a tampered body is reported as a mismatch, not silently accepted.
- [ ] **Step 2: Run and confirm failure.**
- [ ] **Step 3: Implement.**
- [ ] **Step 4: Prove it by hand** — `curl` the canonical source, `sha256sum` it, and compare against the `contentHash` in `/chain.json`. If a reader cannot do that with two standard commands, the design is wrong. Paste the commands and output into your report.
- [ ] **Step 5: Run the suite seeded and cleared, then commit** — `feat(site): verify one transaction from its raw text`

## Self-Review

**Spec coverage.** §7 in full: streaming per-block verification (Task 1), transaction-hash recomputation and the forged-title case it exists to catch (Task 1), proof-of-work against each block's own difficulty (Task 1), per-transaction verification from raw text (Task 2), and the one-module constraint (both, by construction).

**What this plan does not do.** Search — a separate plan. It also does not verify the **open block**: pending transactions have real hashes but no mined block, so there is no proof-of-work or Merkle root to check. If Task 1 shows anything about them, it must be clear that a different and weaker thing was checked.

**Risk flagged for both implementers.** Every serious defect on this project was found by driving the real workflow end to end, and none by the suite passing. A verifier is especially prone to this: it is easy to write one that reports success because it checked nothing. Tamper with the data and confirm it *fails* — a verifier that cannot fail is worse than none, because it manufactures confidence.
